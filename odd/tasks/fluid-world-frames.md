# fluid-world-frames

Make the title's world frame time acceptable: remove the host-side stalls measured in the world (2780 ms/frame, 0.4 fps) without changing what the title renders.

## Specs

S1. The user's requirement, verbatim: "procede ya que debe funcionar fluido el juego a todos los fps posibles has todo lo necesario para que corra bien".

S2. Baseline to beat, measured in the world with the `diag` build and the same driver used for verification (`VICTORY_GPU_TIMING=1`, `VICTORY_D3D12_DRED=1`): 2780 ms/frame average, `textures` bucket 1188 ms of which 964 ms is the `MAPPING` lock wait, "the title had not submitted" 553 ms, `copying back` 212 ms, heap-buffer pass 253 ms, `on the GPU` 218 ms. Every accepted change is proven by an A/B run of that same driver: ms/frame must go down and the visual output must not regress.

S3. The GPU is not the target: per-command GPU timings are 0.7-1.25 ms/frame and the card reads 2-10% busy. Work that only moves cost between CPU buckets, or that removes GPU work by dropping draws, does not satisfy S1.

S4. A shader or pipeline that cannot be translated is out of scope for frame time; the 745-4067 permanently dropped draws per report window remove GPU work and must not be "fixed" by dropping more.

S5. The user's report, verbatim: "asi esta apareciendo la imagen corrigelo", with two captures of the prologue showing (a) a character silhouette smeared across half the frame with straight clipping edges and (b) a hard-edged black rectangle in the upper right. Requirement: the world must be drawn from the payload of its own frame. No draw may consume another frame's meshlet payload, and no geometry may be drawn from a buffer whose fill was skipped.

L33 (evidence, the 281 ms stall has ONE cause and removing it the obvious way is a loss): the line "of the waiting for the card in settles, per frame, by what settled" reads `title memory read 281.1` with every other entry 0.0 (`arm-default-20261125-064213`), so the whole host stall is the pre-submit gate at `host.rs:3984-3991` (WHY_READ). A delegated attempt held the blocked submission behind the landing instead of blocking the submitting thread (`Line.landing`, `LANDED`, `Held::Landed` in `queue.rs`): the gate did fall to **24-88 ms**, and the frame got **worse** — 1090.2 and 1355.5 ms mean against 595.9, with the card's busy share collapsing from 79-80% to 19-29% (`nothing of ours queued` 103 -> 800-1180 ms). Reverted, tree clean. **The wait is where the host's work overlaps the card: removing it does not save 281 ms, it trades a host stall for a card stall.** The same attempt proved that comparing against a flying Flight's own ranges instead of `line.written` is a no-op (`join_ranges` only merges overlapping or touching ranges), so the gate is a true read-after-write, not over-blocking. Root of the read: `draw.rs:463-466`, where a root view whose GPU address is not 256-byte aligned (the console needs 16) is served by a scratch copy filled by `defer_fill` **from title memory**. The card's own copy of that memory already holds what the shaders wrote, so the fill could be a `CopyBufferRegion` from the shadow's buffer instead, which removes the title-memory read without touching submit/landing.
